# Capacity ownership on stock Pi 0.99.0

Nunc remains a standalone extension. This repair changes only this project: no Pi core edits, private hooks, installed-package patches, scheduler replacement or prompt replay.

## Separate planning from main admission

Pi owns normal compaction scheduling, output sizing and provider overflow recovery. Nunc's memory/retention planning continues to reserve output, safety and post-maintenance growth. Crossing that planning target alone must not reject an ordinary main request. Encrypted-reasoning output proxies are retention/forecast costs only: current_turn can discard earlier reasoning even when signed items are transported. The new message-level proxy is not added to fresh/trailing hard admission or a valid receipt. Planning/UI expose its basis and missing-mode/usage uncertainty separately; generic visible estimates and existing U/old-M protections remain intact.

On the already supported native context-clamped and uncapped routes, main admission uses `min(model.contextWindow - serializerOutputFloor, configured inputLimit)`; the floor is 16 for capped Responses and 1 otherwise. The explicit input limit remains binding. The native serializer still owns the actual output cap; uncapped routes retain no cap. Unknown context-sizing routes retain fixed-output-reserve accounting until their native behavior is verified.

For the default 272000-window Codex route:

- Pi compaction threshold: 255616.
- Nunc memory/retention input planning target: 254592.
- Nunc main input guard: 271999.

A 254598 estimate is above the memory planning target and below the main guard. It delegates normally, including when default `keepRecentTokens=20000` would leave Pi without a summarizable prefix. This removes the independent soft-budget overflow that caused the reported recurrence. Main observations expose `plannedInputLimit` and `inputExceededPlan` separately from the enforced `inputLimit`; plan overruns do not emit warning spam or mutate settings.

This deliberately replaces the old contract that enforced the output/safety planning reserve on main requests. Safety and growth budgets guide extraction and native retention planning. The system distinguishes the soft memory target from the active patch growth limit:

- In maintenance extraction, `memoryTarget(config)` returns strictly `config.memory?.targetTokens ?? 8192` (`accounting.ts:158`). This advisory target feeds into planning alongside fraction and maxTokens: `memoryPlan.memoryLimit = Math.floor(Math.min(config.memory.fraction * Math.max(0, available), config.memory.maxTokens ?? Infinity, memoryTarget(config)))` (`accounting.ts:171-178`). Extracted candidates and declared required items are not rejected for exceeding this organizing target in the absence of an explicit hard cap; optional items are pruned when required items alone exceed the target.
- In manual memory edits (`nunc_memory_patch`), the growth limit is `limit = Math.min(memoryTarget(config), explicitHard ?? Infinity)` (`manual.ts:339-348`). Under `manual.ts:221-226`, budget rejection applies exclusively to edits that actively increase total memory tokens (`grew = budget.tokens > current.budget.tokens`), with distinct failure modes: `unknown-budget` triggers when the budget estimate cannot be computed (`budget.unknown`), while `overbudget` triggers when the growing estimate exceeds the known limit (`budget.limit !== null && budget.tokens > budget.limit`). Non-growing edits, shrinking updates, and recovery operations are exempt from growth rejection, allowing repairs and deletions even when current memory already exceeds the budget ceiling.
- When explicitly configured, `memory.hardMaxTokens` bounds final saved M by failing oversized required candidate sets with `CAPACITY` during maintenance extraction and capping the manual growth ceiling. An explicit hard cap applies strictly to prospective candidate admission; it does not retroactively shrink already-saved M or guarantee correct forgetting.

The next actual main request is measured against its authoritative Context. Model-window guards are heuristic checks, not tokenizer proofs or guarantees about simultaneous native input plus maximum output.

## Protections that remain

Nunc checks final Context shape, associations, native media and configured overhead before delegation. Main usage attribution is bound to an actual sent request and a valid completed response. Earlier compatible receipts can be selected after a newer incompatible F; accounting pins that receipt's assistant instead of Pi's latest usage. Trailing growth, including custom/tool/media/metadata/append, is still charged. Supported payload text/metadata growth is charged against the same main guard; native serialized output room is checked for text append. Unknown rewrites, altered models, output-cap expansion, unsupported media and actual admission overruns still fail before HTTP. Independent calls retain their own native behavior. A bounded in-process receipt list is not a call cap; user `maxCalls`/`maxTotalTokens` remain omitted/null in this project.

Default extraction uses full source and automatic capped output. The minimum reserve `min(8192,C)` is checked before requesting the desired `min(32768,C)`; final cap cannot exceed the complete frozen request’s remaining window after safety. Explicit numeric settings stay fixed, and uncapped APIs/auth routes keep planning-only output with no serialized cap. Status separates desired, actual and limiting reason; no cap doubling or retry follows a failure. Pi trigger/reserve settings and main admission are unchanged.

Extraction retains its separate output and safety reserve, complete delivered-source projection, one configured tool-text reduction, any explicit hard cap on final M, and joint retention of all declared required items. The planned memory limit (from fraction, maxTokens, and advisory memoryTarget) can be zero when historical F is stale or exceeds the trigger; required facts may exceed it without a default hard cap. Optional items are discarded when required alone is over target. Only an explicit `memory.hardMaxTokens` can make an oversized required set fail with CAPACITY; no partial candidate is admitted, no body is truncated, and no fallback summarization is triggered. An explicit hard cap governs candidate admission during maintenance without retroactively shrinking existing saved M or guaranteeing correct forgetting. A successful candidate is not vetoed solely because historical F plus projected growth predicts a next-main overflow. Temporary context/payload additions never become persisted source. Only a native checkpoint establishes saved memory; `reject` does not mean `sent`, and a candidate does not mean `saved`.

Image accounting uses the same planning semantics as text: absent `budget.imageTokens` falls back to Pi's per-image heuristic; an explicit positive value overrides it. Missing configuration alone never rejects a native image. Compatible usage receipts account for the historical prefix without estimating its images again; newly appended images and reshaped extraction requests are estimated. Main/extraction limits still apply to those estimates. Underestimation may reach the provider and trigger native overflow handling; this is no hard-capacity guarantee. Image capability checks, native image preservation and failure-without-commit remain unchanged.

## Recovery boundary

Actual capacity errors retain native bounded overflow and threshold recovery. In observed stock Pi sessions, automatic threshold checks run at distinct native lifecycle evaluation points: `prompt()` invokes `_checkCompaction(lastAssistant, false)` before appending a new user prompt when prior assistant history crossed threshold, and post-run completion invokes `_checkCompaction(assistantMessage)` when the completed turn leaves context above threshold (`_compactBeforeNextAssistantResponse` is subsequent multi-turn agent loop preparation). Each maintenance opportunity dispatches exactly one engine extraction transaction; Nunc never initiates retries, automatic prompt resubmissions, or model repair loops. When an explicit-hard-limit required-capacity maintenance fails, compaction cancels cleanly: no compaction checkpoint is written, no default summary fallback runs, and saved M and K remain unchanged. In these observed scenarios, each opportunity evaluates its distinct causal input and terminates without unbounded loops, duplicate prompt delivery, or duplicate tool effects. Nunc does not claim a universal two-call ceiling across arbitrary multi-turn host loops or general termination beyond bounded proof. Automatic compaction disabled stays disabled; explicit `/compact` remains available. Nunc does not abort then resubmit a user prompt, read pending queues, force a cut, or patch Pi's recovery state.

Stock Pi can return before `session_before_compact` when its default character-based preparation finds no summarizable prefix. This project cannot fix that host path. The repair avoids entering it merely because a request exceeds Nunc's soft planning target. A complete extraction `stop` is not discarded because reported input+cache exceeds the catalog window; that path cancelled auto-compaction and retried the same oversized turn. Explicit extraction `inputLimit`, output caps and any explicit saved-M hard cap still bind. Default-target overflow alone saves a complete required candidate; current saved-M occupancy reduces the next history target. This never moves the current cut after extraction or adds a maintenance retry. True oversized/unretirable input or a failed native/provider recovery can still require operator intervention; no automatic-recovery guarantee is claimed.

## Maintenance feedback and explicit recovery

Each `maintain` call generates at most one model request. `maxRetries: 0` disables provider retries; Nunc does not resubmit full, reduced, malformed, disconnected or cancelled requests. A provider rejection cancels native compaction and leaves old M, original source and the checkpoint unchanged. `nunc:maintenance` remains attempt evidence, not a save receipt. Failure may append a lightweight `nunc.maintenance-calibration` custom entry containing overflow and/or measured input evidence. Plain custom state is excluded from model context and `project.active`; it neither retires history nor changes M.

`observations.providerOverflow` uses Pi AI's `isContextOverflow(response, model.contextWindow)` and records provider/API/model, `full` or `reduced` mode, original source entry IDs, raw estimated input, resolved extraction input limit, output reserve, reported context input and provider `errorMessage`. Rate limiting (including HTTP 429), disconnects and cancellation do not become context refusals. SDK-detected length overflow is recorded too. A complete valid `stop` above catalog occupancy keeps the existing acceptance behavior: its usage can calibrate planning, and the successful checkpoint does not save it as a refusal.

On the next **native maintenance opportunity**, including explicit `/compact`:

- `auto` applies one bounded `reduceToolBodies` pass before dispatch when a full refusal's original source IDs and contents remain the current active prefix. Later delivered messages may extend that prefix, including changes in cleanup eligibility. The heuristic cannot authorize a blind full resend. Every omission is marked; user/assistant text, tool arguments and images remain unchanged. If nothing can be reduced, maintenance returns `CAPACITY` with zero dispatches.
- Explicit `full` never silently downgrades. The same full source and resolved input/output limits return `CAPACITY` without a model request. To permit marked reduction, select `extraction.toolResults: "auto"` in the existing optional Nunc configuration; persistence of feedback itself needs no configuration file.
- A previously refused reduced request with the same complete source IDs/contents, head/tail setting and resolved input/output limits also returns `CAPACITY` with zero dispatches. Further explicit attempts need a meaningful change, such as a smaller tool-body reduction setting, an edited/replaced source, changed effective capacity, or a larger model. Extending the source permits one newly bounded attempt; applicable older full evidence still requires reduction in `auto`.

Feedback follows the selected branch and exact provider/API/model identity. Source-content digests detect native edits under unchanged IDs. Effective model/budget changes invalidate old bindings; reduced refusals also bind the head/tail setting. A plain state append does not invalidate a binding. Full and reduced refusals and the latest valid measurement are selected independently, so an unknown-usage failure cannot erase prior full evidence or a positive correction. Navigating to an unrelated branch, dropping the original active prefix, or changing its content prevents reuse. Historical records are not deleted or imported from abandoned branches.

Valid **maintenance** input usage saves `undercountTokens = max(0, actualInputTokens - estimatedInputTokens)`, with `actualInputTokens = input + cacheRead + cacheWrite`. No missing usage is fabricated and no main-response receipt is used. Successful checkpoints bind the measurement to unchanged original K (including already-selected cleanup) so it remains applicable after retiring B, while retaining the measured request's original source IDs and counts as provenance. If a successful response has no valid input usage, an applicable previous measurement can survive that checkpoint. Closing the runtime, opening the same persistent session with `SessionManager.open`, and constructing a fresh runtime restores this state without `--nunc-config`.

The positive `calibratedUndercountTokens` correction is added to maintenance preflight and `resolveExtractionRequest`, including automatic output-cap resolution. `extractionTokens` remains the raw heuristic; `extractionPlanningTokens` includes the correction. Measuring against the raw baseline prevents repeated subtraction of an earlier correction. Accounting marks `maintenance-usage-undercount` uncertainty and `/nunc details` labels the correction as prior maintenance usage with uncertain applicability. This is an observed additive correction, not a tokenizer guarantee or a fixed extra reserve; main estimation/admission stays unchanged. A correction that still cannot fit returns `CAPACITY` without a request. Nunc never schedules an automatic retry to consume the saved evidence.

## Regression evidence required

- Exact `254598` usage-backed request delegates under defaults instead of producing local CAPACITY.
- High usage/short visible history with keep=20000, auto enabled and disabled; no fabricated maintenance or duplicate input.
- Fresh estimates and supported payload growth can cross the planning target while fitting main admission.
- Explicit input limits and model-window overruns still reject before transport.
- Repeated native threshold rollovers save checkpoints and continue, with original input/tool delivery preserved.
- Declared required items are retained jointly; optional items are dropped by priority without skipping required items or disturbing natural order.
- Required set exceeding the independent saved-M hard cap yields explicit CAPACITY failure, unchanged M/K, no default compaction fallback, single tool execution, and bounded host recovery across manual, threshold, and overflow paths with verified opportunity counts.
- Existing extraction, payload, cancellation, native loader/transport and persistence checks remain valid.
