# Nunc：让有限上下文支持持续工作

状态：**IMPLEMENTATION_IN_PROGRESS — 原生维护与独立容量检查方案**。更新于 2026-09-06。

本文定义 Nunc 完整项目的交付要求与当前推荐方案。策略资产、维护引擎和 stock Pi 适配器已在仓库中；真实模型续做及最终验收未完成。本次修订采用已交付历史的维护边界，保留 Pi 原生提交和恢复，独立检查新增输入造成的容量突增。交付目标覆盖本文全部必要行为、失败与恢复、兼容和验证要求，最终按 §8 对整合后的项目验收。设计选择来自项目动机、机制推理、公开 Pi 接口及有限的受控运行观察；不以 benchmark 胜出作为交付条件。

产品约束包括 session 范围、原文保留、记忆有界、增量维护和宿主持久化。明确标为推荐、示例或可选的内容保留设计空间：字段示例、比例起点、预算选择算法、容量恢复方法和模块划分允许按目标 Pi/API 采用等价实现，多个备选路径无需同时支持。选择替代实现仍须满足同一必要行为和边界。

## 1. 原始问题与产品目标

Agent 的上下文承担正在工作的状态：当前在做什么、为什么这样做、哪些条件仍然有效，以及接下来需要什么。会话持续增长时，应让这份工作状态保持有限、可理解且能继续推进。

Nunc 提供一个随工作向前移动的有限“现在”：近期工作保留原文，离开近期窗口后仍影响当前会话的信息进入有界工作记忆，其余内容退出模型可见上下文。记忆按继续工作的需要维护，无需覆盖全部历史，也无需反复把全部旧信息写得更短。

遗忘用于控制有限上下文的负担。长期事项由正常的代码、文档和其他外部产物承担；Nunc 不代替项目记录流程，也不自动将记忆写入外部文档。

范围：

- 仅做独立 Pi 扩展，不支持 Codex CLI/App；不依赖其他扩展或子代理系统，不要求替代启动器，不修改 Pi 核心或访问私有会话字段。
- 一个持续 session；不自动跨 session 携带记忆，不做主动记忆搜索。
- Pi JSONL 保留完整。同 session 恢复时加载当时的记忆和原文窗口，不重新向模型展开全部历史。
- `/new` 从空记忆开始；用户明确选择的 tree/fork/clone 遵循 Pi 的活动路径语义。
- 主 agent 继续正常读代码、文档和运行工具。Nunc 自己不查询外部来源，不回读已退役历史。
- 普通工作期间没有记忆工具调用要求、使用次数统计或额外评估模型。

## 2. 推荐结构：重叠原文窗口与有界工作记忆

```text
维护冻结时： F_t | render(M) | R_t，R_t = B | K
维护之后：   F_next | render(M_next) | K | D
普通请求：   使用当时的 F、全部 M 和已经交付的活动原文
```

- `F`：Pi 在相应时点提供的有效指令、工具定义等；维护使用冻结时的 F_t，后续请求使用其实际 F。
- `R_t`：维护冻结时，当前选定活动路径上已交付、可通过公开 Pi 投影得到的完整活动原文。已交付的新用户消息、工具结果和所需自定义消息均在其中。
- `B`：本次即将退出的连续旧前段。
- `K`：继续保留的原文后缀，其内容和顺序不由维护模型重写。
- `M`：近期原文之外，继续这段会话仍需携带的少量工作信息；每次主请求都自动包含全部 M。
- `D`：冻结之后才实际交付的消息，包括此前仍排队或尚未发布的新输入。它们不进入已经冻结的维护请求，交付后按原文进入主请求；未来输入不得被提前展开。

这是对早期“维护必须包含等待下一请求的全部新消息”要求的明确修订。Pi 的预先维护早于部分新输入和队列交付；采用已交付边界可复用原生生命周期，无需猜测、提前消费或重放队列。代价是本次保留选择不能利用 D 中稍后出现的新线索。已经交付的纠正、未完成工作和持续约束仍须发挥效力；D 中的纠正先作为原文影响工作，在下一次维护中再更新 M。

M 的维护问题是：

> 假设维护后只剩 F、K 和正常工作工具，继续这段 session 还缺什么？旧 M 中哪些内容仍补这个缺口，B 中哪些内容需要带走，哪些内容已被后续进展纠正或取代？

“继续工作”包含当前目标、仍未完成的工作和持续有效的约束，不限于紧接着的一个工具调用。短暂切换话题，不自动取消尚未完成的事项。

M 可以留空，也可以没有新增内容。已可靠保存在已知产物中的内容通常只需留下必要位置和用途；无法从剩余上下文或已知产物恢复的精确条件更值得携带。Nunc 不为确认产物内容而额外取数。

### 2.1 最小记忆结构

推荐用可独立更新和退役的小块表示 M：

```ts
type Slot = { id: string; text: string };
```

一条可以是几句笔记、一个带适用条件的结论、必要代码或局部步骤。条件、结论和状态需要一起理解时，放在同一条内；不把每个名词机械拆成独立条目，不建立依赖图。

不强制目标、约束、事实、决定等统一分类。表达形式由策略指导；ID、容量和变更合法性由代码管理。Slots 方便局部维护，不承担预测未来用途的算法能力。

未修改、未退役的条目直接复用正文。允许局部纠正、替换和合并；修订不能变成每次重新生成全部 M 的例行动作。持续有效的信息无需靠频繁被提及来续期。

### 2.2 原文何时退出

采用批量滚动：输入达到工作触发线 H 时，移出 B，保留显著重叠的 K，令维护后的上下文回到较低的占用水平 L。

```text
随着新工作增长至 H
       ↓ 一次维护并移出 B
回到 L，保留 K 和仍有效的 M
       ↓ 随着后续工作继续增长
```

H 控制工作规模，H 与 L 的距离控制维护频率。模型的有效容量约束它们的可行范围；不以接近模型容量耗尽作为产品目标。

保留 K 的目的，是让当前工作直接依靠近期原文继续。B 在退出时才接受提取，维护请求可以利用较新的 K 判断旧猜测后来是否成立、哪些尝试已被排除，以及当前真正需要什么。这使提取发生在具有更多后续信息的时刻。

不逐消息移动切点，不等待模型判定“整个任务完成”。在容量范围内选择合法的消息边界，维护工具调用与结果关联，并尽量保留当前工作的近期连续单元。一个长期任务不能无限阻止滚动。

B 退出和 slot 退役仍有明确边界。连续性来自保留 K 与未变化的 M，不承诺任意历史细节永远可见，也不承诺 KV cache 跨滚动不变。

## 3. 一次维护：模型判断内容，代码执行预算

维护由 Pi 扩展发起，使用主 agent 当前模型。正常路径是一轮普通模型请求，没有独立 extractor agent、工具执行循环或固定的小模型。

1. 冻结本次活动路径、M、B、K、模型和策略；计算输入输出预算。
2. 将完整 M/B/K 作为维护来源，提出 §2 的续做问题，给出 M 的容量上限，明确 B 即将退出、K 将继续保留。
3. 模型提出新增、删除、局部替换或合并，以及容量不足时的保留选择。
4. 代码校验结构、引用、响应终态和取消状态；构成候选 M，执行整条预算选择。
5. 检查 `F + render(M_next) + K` 的容量、合法边界及维护后增长空间。
6. 校验成功后向 Pi 返回一份完整 snapshot，由 Pi 持久化和重建；交付前不提前修改已保存的 M 或原文边界。

### 3.1 内容判断的优先顺序

维护模型先处理明确的修正和失效，再决定需要新增什么，最后在有容量竞争时比较保留价值：

- K 中新的明确要求或验证结果，可以改变 B 和旧 M 的含义。将猜测、计划、尝试和已经验证的结果区分开。
- 已完成的过程通常可以退出；完成过程中得到、仍会影响后续工作的结论可以继续保留。
- 优先考虑忘记之后容易导致错误行动、重复失败或用户重述的信息，并考虑从剩余上下文及已知产物恢复它的难度。
- 在候选价值接近时考虑长度和重复；不要求把 M 填满。
- 不把提及频率、存活时间或模型自报“使用过”当成真实使用价值，不引入强制衰减、永久 pin 或权重表达式。

用户指令、工具观察和助手推断具有不同含义。工具失败描述执行状态，不能自行取消用户目标；助手的反复复述也不能提升某个猜测的证据等级。

### 3.2 与 K 的重叠

如果某条 B 中的信息已经在 K 中完整、可直接理解地存在，通常可以暂不复制进 M。承载它的 K 原文未来进入 B 时，还会再次获得提取机会。

同一主题仍在出现，不代表信息已被完整保存。例如 K 中的 Node 22 测试结果不能覆盖 B 中的 Node 18 兼容要求。比较时包含条件、否定和当前状态，不能只比较关键词。

K 中新出现的纠正可以立即更新旧 M。必要的重复允许存在；为强求零重复而删除续做所需的联系不符合目标。

### 3.3 增量协议与容量处理

一个可实施的请求结果示例：

```json
{
  "add": [{ "key": "new1", "text": "只有成功提交前可以重试；提交成功后再次执行会重复扣款。" }],
  "remove": ["s4"],
  "priority": ["new1", "s2", "s8"]
}
```

例中旧集合为 `s2/s4/s8`。替换或合并可表示为删除旧条目并新增替代条目。使用本示例协议时，priority 完整列出删除后存量与新增候选，每个引用恰好一次，避免遗漏被悄悄解释成退役。

候选集合未超预算时无需容量淘汰；超预算时按模型给出的保留顺序选择能完整放入的条目，放不下的整条跳过。不在正文中部强行截断，也不为了装下而要求整份 M 重写。已经明确错误的旧结论，不因替代条目最终放不下而恢复。

保留优先级不改变普通请求中的排列。存量条目保持相对位置，新条目追加，避免仅因排序变化重排 M。渲染中的 ID 和包装计入预算。

上述字段、完整排序的输出时机以及 JSON/工具承载方式属于实现协议。产品要求是模型给出可执行的变更与保留选择，代码保证预算和条目边界；不把这一份 JSON 形状当作不可替换的架构。

## 4. 窗口、记忆与模型预算

只需区分三个用途：工作触发线 H、记忆上限 M_max、原文保留比例 q。L 由实际保留下来的 M/K 决定，无需再配置一套独立阈值。

统一按完整请求输入的 token 口径核算：

```text
主请求安全输入上限 = 有效模型窗口 − 本次输入准入所留输出空间 − 估计与新增内容余量
A = min(H, 主请求安全输入上限) − F 的估计长度
M_max = min(memory.fraction × A, 可选 memory.maxTokens)
K_target = q × (A − M_max)
L = F + render(M_next) + 实际 K
```

省略 M 的绝对上限时使用比例。A 必须为正；memory.fraction 在 [0, 1) 内，q 在 (0, 1) 内，绝对上限若提供则为正数。输出预算、thinking、多模态和 provider 的独立输入/输出限制按实际请求语义计算；最大输出能力不等于每次应该预留的输出量。

已验证的 Pi 原生按剩余上下文裁输出路径，以 compaction reserve 与最大输出能力的较小值作为主请求输入准入余量，且覆盖序列化输出下限；保留 Pi 实际输出设置。该余量不代表原生输出上限，Nunc 与 Pi 的估算器不同，不能据此声称 Nunc 输入估算加实际输出上限同时小于窗口。未序列化输出 cap 的路径继续完整预留；具体适配范围见 [PI.md](PI.md)。

还要单独检查完整 extraction，包括 M/B/K、控制消息、输出协议、提取输出和余量。原生前缀已经包含 F/M 时不重复计数。cached tokens 仍占上下文；未知 usage 不当成零。

正常滚动应能容纳完整 extraction，H 必须留出相应空间。若不能容纳，应在配置上降低 H 或选择开销更小的完整请求形态。不要把每轮有损删减输入作为默认运转条件。

q 要让 K 足以承接近期工作，同时释放足够空间。较大 q 增加连续原文，也提高平均输入长度和维护频率。参数可从 q 约 2/3、M 约占可用工作预算 1/10 起步；实施时允许调整，验收关注预算、连续性和增长空间，不固定这些数值。

按合法边界取整后，L 必须低于实际触发线，并留出继续增长的空间。调低 H 时同步重算 M/K，避免维护后立刻再次触发。单个不可分大消息无法满足时，明确报告限制。

模型切换时读取新的有效容量，重新核算两类请求及 M/K。大窗口切到小窗口可能连维护来源都装不下；应在可容纳的模型上先整理，或走 §5 的容量处理，不能只缩小最终 M 就声称完成适配。

## 5. 工具结果与请求构造

### 5.1 完整来源与正常路径

普通请求保留已经交付的活动原文，包括工具正文，直到相应 B 正式退出。extraction 使用 §2 冻结的完整 M/B/K；Nunc 不增加普通推理的工具结果隐藏层。

维护来源以冻结时当前活动路径的公开 Pi 消息投影为界，保留工具名、参数、调用/结果关联、成功或错误状态和所需自定义消息。它不包含尚未交付的 D，也不要求恢复 Pi 已截断的输出、打开日志附件、重读文件或查询已退役 JSONL。

维护来源与请求容量检查是不同的观察边界。稍后发生的 system/tools/options 注入、临时 context 变换或 provider payload 改写不自动回填已经冻结的来源。普通请求的容量检查仍须覆盖所声明支持配置下的实际输入及选项；未经验证的额外改写不得被表述为完整兼容。

按目标 Pi/API 选择适用的承载形态；完整交付可以采用其中一条满足要求的路径，无需同时实现两条。两种形态表达同一维护语义：

- 目标 Pi/API 能保持前缀时，沿用模型、有效 system、工具定义、消息块和有关选项，在尾部追加维护指令和 M/B/K 范围说明。结构化结果不进入业务工具执行循环。
- 无法可靠构造相容前缀，或其输出方式不适合时，使用短维护提示和显式 M/B/K transcript。保留完整可见证据，按实际 usage 计费。

不为强求缓存而复制 Pi transport、实现全 provider 的请求改写框架，或规定必须切换到唯一 extraction tool。历史重新包装、修改 system/tools/options 都可能改变缓存匹配；原文保留本身不构成缓存保证。

滚动期间 M 和原文前缀发生变化，后续主请求可能需要重建缓存。因此通过批量滚动摊薄维护成本，普通轮次保持 M 和既有原文稳定；不每轮维护 M。

### 5.2 实际容量不足

缓存过期、工具结果年龄大或看起来冗长，都不单独触发有损过滤。以下缩减只用于完整 extraction 实际无法容纳的情况，不修改普通主请求中的原文 K 或 D：

1. 若实现已支持开销更小的完整请求形态，可以先尝试；不为此强制增加第二种请求实现。
2. 完整输入仍无法容纳时，可按配置选择一种有界的缩减方法，例如对超长工具正文做有省略标记的 head/tail 处理，或减少 extraction 中用于参考的 K。保留最新用户要求、纠正和工具关联，实际返回 Pi 的 K 不因此修改。具体取舍服务于当前输入，不要求实现两种缩减方法，也不固定“永远先丢 K”的顺序。
3. 不暗中截断用户指令、存量 M 或工具调用参数。记录哪些输入被省略，不能声称已核对不可见证据。
4. 所选处理仍不能容纳时，显式取消并说明容量原因。顺序分块或多阶段提取的恢复流程不属于必要交付范围。

head/tail 可能丢失中部关键证据。图像、PDF、音频等内容优先使用目标 API 支持的原生块；文字占位符不能替代视觉或音频事实。不支持时说明限制。

### 5.3 主请求容量检查

维护控制工作规模；请求容量检查决定这一次完整输入能否发出。维护后占用 L 不包含尚未交付的 D，任何固定 reserve 都不能保证容纳任意大小的 D。输入交付后，使用实际模型、system/tools、消息、多模态及输出选项重新检查主请求安全输入上限；工作触发线 H 与此检查不构成两个各自维护 M 的调度器。

- 可通过退出旧历史恢复的本地容量拒绝，交给 Pi 有界的原生 compaction/retry；不发出明知超过已检查预算的请求，不要求用户重新提交同一条输入。
- 本地拒绝必须与 provider 实际报错、用户取消及维护失败区分。用户取消不得被解释成容量不足并自动恢复；容量检查不得撤回排队消息、丢弃扩展通知、改变排队顺序或重复追加输入。
- 自动 compaction 关闭时，检查不擅自开启维护；说明需要显式整理、减少输入或选择合适模型。维护失败或取消时，不提交候选，不通过递归重试掩盖失败。
- 单条不可分输入本身超限、没有合法可退出前段、预算无法成立或配置不受支持时，明确诊断限制。不得暗中删减用户输入或以无限整理代替错误处理。

## 6. Pi 接入与持久化

### 6.1 宿主负责维护生命周期

维护生命周期复用 `session_before_compact`：Pi 提供调用时机和活动路径，Nunc 返回 `summary/details/firstKeptEntryId`，Pi 跳过默认摘要生成，保存并重建上下文。正常路径只产生一套维护结果。该 hook 读取调用时已经交付的历史，不负责提前读取宿主局部 pending 队列；之后交付的 D 由 §5.3 的请求检查处理。

Pi 已有的自动触发线为：

```text
H = 当前 Pi 模型 contextWindow − compaction.reserveTokens
```

以生效的 Pi 配置表达 H，不再增加一个各自触发的 Nunc 调度器。增加 reserve 可以提前维护；它同时必须满足主请求和 extraction 的余量。工作预算的选择无需沿用宿主默认数值。

当前检查的公开 ExtensionContext 没有修改 reserve 的接口。可以通过 Pi 的已有配置选定工作范围；不得承诺扩展已经支持自动按模型改写阈值。自动配置若成为实际需要，在目标 Pi 上选择公开接入方式，不把私有 hook 或 core patch 设为默认前提。

`keepRecentTokens` 是 Pi 准备阶段的初始切点参数，Nunc 再按自身预算确定 K。过早触发但宿主保留量覆盖全部历史、或无法形成可退出前段时，preparation 可能不进入 hook；reserve 和该初始保留量要一起检查。

显式 `/compact` 和宿主溢出恢复也进入同一维护语义。关闭 Pi 自动 compaction 后，需要显式触发。当前 `ctx.compact()` 走先 abort 的手动路径，不从每次 context 回调直接调用它并承诺无中断滚动。

接口依据：[Pi 配置说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/settings.md)、[Pi compaction 与扩展接管说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)。本次接入调查对照 stock Pi 0.85.1；已整合引擎的锁定检查环境仍为 0.85.0。Pi 生产者须统一选定目标、依赖和回归证据；调查版本不等于已通过产品验收，也不构成未经验证的版本兼容承诺。

### 6.2 一份快照，一次提交

推荐在一个 CompactionEntry 的 `details.nunc` 保存 slots 和最少格式信息，summary 由同一候选渲染。Pi 是唯一持久化所有者；不另建数据库、双写账本、hash/CAS 协议或历史审计副本。

同 session 恢复使用当前选中路径最新的 Nunc snapshot。外部/旧式 summary 可作为一个文本 slot 接入后按正常规则维护，不自动导入其他 session。

完整响应终态、合法引用和预算检查都通过后才返回 snapshot。截断响应即使包含可解析 JSON 也不能提交。结构失败可做带校验反馈的有界修复，建议最多一次；仍使用冻结来源并重新检查请求容量。取消、修复失败或模型/path/session 改变时，不提交过期候选。

提取、校验失败或交付前取消时，Nunc 显式返回 hook 的 `cancel: true` 并说明原因，不修改已保存的 M 或原文边界。不能用空返回表示失败，否则 Pi 可能继续生成默认摘要。

候选交付后的 append/rebuild 及错误处理由 Pi 负责。Nunc 不承诺为宿主写入或重建失败另加事务回滚，也不自行重放提交；认证和路径复制同样沿用宿主能力。

firstKeptEntryId 指向上下文可见的合法边界。主模型和后续维护只使用最新 M；原生重建中落入保留范围的旧 compaction summary 不得再次成为活动记忆。保留跨旧 checkpoint 的合法 K 重叠。推荐用窄 context 规范化排除被替代的 compaction carrier，不改写 K，不将所有切点一律移到最新 checkpoint 后来回避问题；保持同一不变量的等价实现可以替代它。

支持范围为 persistent session；同时启用多个返回自定义 compaction 的扩展不在支持配置内。与其他扩展的启停由各自配置处理，Nunc 不识别特定扩展或替它修改状态。

### 6.3 独立请求检查与接入职责

记忆保存/重建的所有者与请求检查位置独立。正式方案保留原生 CompactionEntry，不采用 CustomEntry 自有 M/K 投影、原始历史双重映射或 SDK host。推荐通过公开 `getProvider`/`registerProvider` 包装当前 native Provider 的主请求入口，保留并委托其原有 transport；包装只负责容量准入和明确错误，不生成记忆、不保存快照、不复制 provider 序列化或认证。

职责边界：

- Pi adapter 提供冻结的活动来源、模型/策略/预算及合法边界，调用现有 engine，校验返回候选与当前 session/path/model/options 仍匹配。
- Engine 返回完整候选或明确失败，不负责队列、请求准入、Pi 提交或恢复。请求检查复用同一容量口径，不另维护一份 M。
- 请求入口检查已经交付的实际 Context 和已解析选项。当前主会话范围内的请求（stock `streamSimple`、当前 session 与非空运行 signal）在预算成立时委托原 Provider。不可容纳的本地主请求返回明确标注 Nunc 来源、可被 Pi 识别的容量错误，由 Pi 原生 overflow 处理进行有界恢复。其他扩展的独立调用原样委托，不套用主会话 payload 限制。主会话/维护的 `onPayload` 以 JSON 字节与输出上限/输入增长/非法字段做有据检查，不以对象原型或全量深相等拒绝观察型回调。末条 user 仅追加一个文本块（必要时先把非空 string 规范成原文块）且其余消息/块/tools/media/control 保持时，按新增输入计入 Nunc 剩余 input。原生 clamp 后的窗口核对使用 Pi 的 `estimateContextTokens` 与追加开销，不把 Nunc 字节估计与已 clamp 的 output 直接相加；不得因此把 Grok 等 W=O 的正常小追加误判为溢出，也不下调原生 cap。
- 维护请求与主请求必须有可验证的来源区分；同模型、同 provider 不足以判断。维护使用一次性 ALS 绑定，不得递归进入主请求准入或启动另一轮维护；同一 context 的重复或绑定改变不得作为独立调用发出。session/signal 只表示会话作用域，不证明唯一调用来源。
- Provider 组合、legacy stream override 和输出默认值按选定版本及声明支持的配置验证。主会话/维护 payload 允许已核算的观察、返回值、原地修改，以及有据的末条 user 文本追加；输出扩大、原文删改/重排、净值抵消、媒体替换、控制变更、非法输入和未核算增长在 HTTP 前失败并给出字段类别诊断，不记录正文。不引入 provider/扩展名 allowlist 或通用 mapper。其他扩展可以增删自身 context 消息；不要求 Nunc 最后加载。不承诺任意改写 Nunc 记忆载体或任意扩展/provider 组合均可覆盖。未经支持的组合明确诊断，不假装已检查完整请求。

TUI 的 `ctx.abort()` 会将排队输入取回编辑器，并清理底层队列。因此不能用这条用户停止操作驱动自动容量恢复；也不在活动请求中等待先 abort 的 `ctx.compact()`。真正的用户取消仍遵循 Pi 的停止语义。等价公开接法必须证明不改变队列、尊重取消、保持单一原生提交和请求前拒绝，不能仅凭 RPC 成功就替代 TUI 证据。

### 6.4 已有证据与未完成项

未修改的 stock Pi 0.85.1 CLI/RPC 上，受控 loopback Provider 探针验证了公开 Provider 包装的请求前拒绝，以及自有快照路径的两次滚动、重启/reload 恢复。另一探针验证了本地容量拒绝经原生 overflow 后的一次 native compaction 和自动续跑：输入只提交一次，拒绝阶段无 HTTP；真实 RPC 取消及维护取消没有被自动续跑。

这些实验分别证明接口机制，不代表推荐组合已交付。自有快照不被本方案采用；RPC 取消接法依赖当前 setup-error 形状，并具有前述 TUI 队列问题。直接取消探针的三个 aborted 终态预期失败仍有效：实际为 error，不能只按 stopReason 判断用户是否被尊重。

实验使用固定 M、受控响应及实验专用预算，没有真实维护模型或记忆质量结论。队列安全的 Provider 准入与原生维护组合、实际 TUI、真实预算/多模态、并发取消、连续重叠滚动和活动路径恢复，仍由接入生产者与后续运行验收完成。

## 7. 策略与配置

Nunc 和验证默认继承 Pi 当前有效 model/provider/options/config，包括启动参数和运行时选择。扩展使用公开 ctx/model registry/request options；独立进程只能解析自己的启动默认值，调用中的 runtime 必须通过公开上下文或普通非秘密参数转发未保存选择，不能假定另一进程能自动发现。不得重建平行模型目录或要求调用者逐项填回默认元数据。

只有命名测试要求需要的差异才作为当前调用/新任务状态的 override，记录理由与实际差异。主请求 output/thinking 不为预算暗改；Codex 等未序列化输出 cap 的 API 预留完整原生输出能力，订阅费用未知保持 null/unknown。

隔离新测试 session、task cwd/文件、输出及有界效果，复用 Pi 现有配置和原生认证 owner。Nunc/runner 不复制整套 profile，不交付 credential-copy、auth-handoff、OAuth store/refresh/login 子系统，不要求 API-key 账户替代 Codex OAuth。凭据值及来源位置不进 stdin/argv/报告。Pi 正常认证解析/刷新及必要持久化保持原生所有权，不承诺 auth bytes 冻结；保护既有 session、保存的 settings/defaults 和其他项目。生产者只用虚构 native profile 与受控服务；真实认证和模型观察由下游 runtime 执行。

一份内置通用策略足够支持混合任务。用户策略文件表达保留偏好、表达风格和纠正原则，不需要随任务切换，不由运行中的模型自动重写。

候选配置：

```json
{
  "policyFile": "./memory-policy.md",
  "memory": { "fraction": 0.10 },
  "rolling": { "keepRecentFraction": 0.67 },
  "extraction": { "toolResults": "auto" }
}
```

- policyFile 可省略，相对路径基准在实施时明确；推荐相对配置文件目录。
- memory.maxTokens 可选，限制 M 的绝对容量。
- 自动维护启停及 H 使用 Pi 现有配置。cached tokens 计入所有容量检查。
- extraction.toolResults 的 auto 表示完整优先、容量不足时有界处理；full 禁止工具正文截断。
- 参数示例可调整；不提供任务类型路由、使用计数、衰减函数、权重 DSL 或跨 session 开关。

策略可以采用自由笔记或偏好的结构化表达，不能取消容量、来源和 session 边界。策略修改在下次维护生效，同一维护及其修复使用同一版本。

## 8. 完整项目交付与最终验收

### 8.1 实施方式与交付边界

实现可以增量推进，优先贯通 Pi 触发 → 合法 B/K → 当前模型维护 → 增量 M → Pi 提交 → 带 K 继续执行及同 session 恢复，以便及早发现接入问题。路径贯通是中间验证点，最终交付必须覆盖本文全部必要要求，包括非正常路径及集成后的行为。

完整项目保持 §1 的产品范围，不增加多用户、跨平台集成、发布承诺、额外 provider 或 benchmark 胜出要求。策略框架、独立后台调度和多 provider 缓存层也不因完整交付而成为必要功能。选择的协议、参数、请求形态和容量恢复方法可以替换；验收检查它们是否保持必要行为，不要求实现所有备选方案。

### 8.3 真实宿主、模型与最终回归

最终整合版本须运行覆盖全部必要要求的完整回归，包含正常、边界、失败、取消、恢复和兼容路径。早期组件检查可以用于定位问题；最终验收仍需要集成后的结果。回归后若修改了影响证据的实现、配置或目标环境，应更新受影响的验证结果；输入未变且仍适用的证据可以复用。

在选定的真实 Pi 宿主上分别核验冻结的维护来源与请求时完整输入，观察生命周期、触发配置、snapshot 提交/重建、连续重叠滚动、继续执行及同 session 恢复。实际 TUI 须覆盖工作中追加指令、排队扩展消息、容量恢复及用户取消；RPC 用于自动化宿主观察，其成功不能代替 TUI 的队列/编辑器行为。Provider 包装须观察主请求与维护请求的区分、恢复后实际委托、model/reload 变化及声明支持的组合，不能 mock 掉被验证的入口。

使用获准的当前主模型取得真实维护与续做证据，记录实际容量、usage/cache usage、任务费用和延迟；未知或宿主/provider 未提供的数据明确标记，不按零处理，也不据此前提承诺缓存收益。接口说明、源码检查、受控响应或单独解析 JSON 的测试不能代替真实模型续做证据。无需真实模型判断的生命周期行为可以使用真实宿主与受控服务验证；固定 M 不证明记忆生成、保留质量或产品完成。

用户已有完整交付预授权；执行前绑定实际新任务 target、解析后的非秘密有效配置、调用/token/time 上限和已知成本约束，不增加自由文本批准或默认继承 receipt 层。未知 subscription billing 不按零或绝对 USD 保证处理。保留防止重复调用、目标混用、额度超限与不明状态重跑所需检查。真实新权限边界或公开机制不能兼顾默认继承与任务隔离时报告具体限制，不扩建凭据绕行方案。

验证记录应说明被测整合版本、Pi 与模型/provider、有效配置、覆盖要求、观察结果和限制。对每项必要要求作交付判断；声明支持的边界须有相应证据，超出支持范围的行为不得表述为已验证能力。

### 8.4 续做场景与效果判断

围绕必要行为选择实际续做场景，优先考虑以下情况；可采用覆盖同一要求的等价场景：

- B 中的判断被 K 中后续证据确认、推翻或改变用途。
- 持续有效的精确条件跨多次滚动仍影响行动。
- 切换话题后回到尚未完成的工作。
- 已完成过程可以退出，同时不重复尝试已排除的路线。
- 巨型工具结果、暂停恢复、大窗口切到小窗口。
- 维护冻结后到达的新纠正与排队指令；容量恢复后继续交付且不重复、不丢失，用户停止不会被自动维护重新启动。

以实际任务结果、约束违例、重复失败尝试、用户重述次数和整个任务的费用/延迟衡量。记忆文本看起来完整或让模型复述标准答案，不能独立代表工作效果。

比较时使用同一模型、工作预算和近期原文量，并给普通 compaction 相当的调参机会。可加入同样能看到 K 的改良摘要，以区分后续证据的作用和增量 slots 的作用。比较用于改善方案和发现应简化的部分，不是开始实现之前的前置证明。

允许失去已退出且未被选中的历史细节。有限记忆无法保证未来任意重访旧话题都完整恢复；长期事项仍由正常外部产物承担。产品要改善的是持续工作的连续性与有限上下文的使用，而非任意历史问答覆盖率。
