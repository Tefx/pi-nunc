# 工作记忆改进方案：明确实施范围与退出机制

状态：已实施轻量关系记忆、提示指导与文档交付，待后续独立 live 观察验证。用户要求明确做与不做：在现有 M 内实施轻量关系记忆，同时修正结果保留、增量更新、退役和收缩；不引入外部存储或独立图机制。最新用户明确授权在后续验证中执行且仅执行一次 fresh isolated MemoryArena native/Nunc 对照（保持既有选择协议，不得为分数重试或调参），作为此前排除项的唯一授权例外；本交付不声称真实模型效果已证。

## 1. 要解决的问题与证据边界

目标是保住完成持续工作所需的目标、条件、有效结果与关联，同时正确更新和退役。当前请求未引用某个结果，不足以证明它无用；一个项目仍在进行，也不足以证明其全部历史细节都必须保存。

已有两轮隔离观察支持以下判断：

- 必要的先前回答完整进入维护来源，但部分主体与结果的关联没有进入模型候选。
- 所有提出的 slot 正文均完整保存；未发现预算淘汰、截断或保存遗漏。新轮 M 为948/850/1107估算tokens，低于1499整理目标，无独立硬上限。
- 新指引已进入请求，但没有消除关联遗漏。官方 PS 新增通过者全部位于维护前，不能归功于该指引。
- 两轮各组 Nunc 都只从空 M 维护一次，尚未验证非空 M 的连续更新与退役。
- 两轮历史、K、维护轨迹和环境不完全匹配，后续指标下降也不能直接归因于某段新提示。

因此优先修正内容选择和退役判断。KG 优于清楚的自然语言笔记、提高预算能解决遗漏、额外审查调用值得其成本，均未得到当前证据支持。

原始结果及限定见本地 `.scratch/memoryarena-sol-rerun-03ecb09/RESULT.md` 与 `INVESTIGATION.md`。生产提示不使用其中的旅行实体、后续问题、gold 或评分规则。

| 内容 | 决定 | 预期收益与复杂度控制 |

| 修正持续范围、结果关联、局部修订与退役判断 | 做 | 直接针对候选遗漏；合并和替换现有提示，不叠加重复规则 |

| 周期审查器、第二次维护调用、自动重试 | 不做 | 不增加调度、运行成本和效果协调 |
| 外部记忆库、额外归档层、退休历史检索 | 不做 | 保持一个 M 状态所有者，避免存储与恢复合同扩张 |

复杂度同时包括代码、提示长度、模型判断负担、每轮 M 占用、调用、验证和维护。生产提示不复制整份方案，不增加逐边评分或保留证明字段。不做的内容不自动成为后续阶段。

## 3. 内容规则：保留什么、写多细、怎样退出

### 3.1 保留依据与当前交付分开

从已交付目标、修订和完成证据判断持续工作的范围。保留有效目标、决定性完成条件、未完成义务，以及理解、完成或验证这些工作所需的当前状态和结果。

已完成子项的选择或结果可以仍是该状态的一部分，无需等到最新请求再次引用。保留时明确主体、结果及必要范围；仅保留名称不代表关联仍然存在。

保留依据应落到具体工作状态、约束、未完成验证或实际恢复需要。项目名称、所属关系、历史引用和“以后可能有用”不能独立使全部细节变成必要项。独立任务分别判断，不发明覆盖全部历史的永久项目。范围确实不明且影响正确性时，保留具体未知项，不假定已完成，也不无限复制背景。

### 3.2 用最简单的足够表达
本轮直接采用轻量关系记忆：涉及对象对应、依赖、替代或条件归属的信息，明确写出主体、关系和结果；复杂限定与结论放在一起。独立事实保持普通句子。模型在现有正文中维护这些语义，代码不解析图。

例如：

```text
导出接口 v2 已选择游标分页，适用于单账户。
恢复步骤依赖该游标语义；跨账户授权尚未验证。
```

语义必须明确；箭头、固定标题、实体类别或边类型不成为协议和验收条件。不把全部文字拆成三元组，也不要求每个实体独占 slot。

| 内容 | 保留粒度 | 删除的冗余 |
|---|---|---|
| 简单事实或单个选择 | 一个自包含句子 | 人为拆出的节点和边 |
| 多对象的有效结果 | 对象、具体选择及必要区别 | 重复过程、无用途别名 |
| 活动要求或依赖 | 精确条件、否定、范围、状态 | 不影响判断的元信息 |
| 当前决定及变更 | 当前有效值和仍必要的替代原因 | 全部旧版本与每次讨论 |
| 确认能恢复的资料 | 准确入口、用途、必要恢复条件 | 大段可恢复细节 |
| 搜索和执行过程 | 影响决定、诊断、恢复或验收的部分 | 完整工具日志与所有候选关系 |

仅在区分身份、时效、权限、证据或恢复确有需要时添加版本、时间和来源。不同范围的同名对象不合并，不生成置信分数。已交付选择与已验证正确的选择保持区分。

任务独有的数量、单位、否定、例外、交互和验证要求保持精确；活动目标与决定性条件直接保留。压缩已确认重复的 F 通用模板和可恢复资料，不假定未来 F 不变或未见产物包含所需内容。

### 3.3 局部更新，不积累全部版本

复用未变正文；有效修订只改变相关部分，保留混合条目中的其他条件和义务。替换、合并和删除前检查完整内容，不凭标题或最近进度判断。

按可独立变化或退役的事项分槽。稳定条件与频繁变化的进度可分开；避免整个项目一个巨大 slot，也避免每个词一个 slot。结果单元自包含，不写“同 s7”或依赖另一个可淘汰条目的定义。共同基线与差异可合并表达，但必须保持独立可理解。

新输入依照来源权限和适用范围纠正旧记忆；新出现的文本不会自动胜过有效要求。维护后的 M 是快照，不能覆盖后来交付的有效修订。

### 3.4 引用不产生独立保留理由

当前有效的依赖、约束和未完成义务支持保留；历史解释、共同出现、所属关系本身不要求永久保留。

| 证据 | 内容处理 |
|---|---|
| 子项已完成，但有效结果仍构成持续工作必要状态 | 保留结果与限定，压缩已无用途的过程 |
| 新决定有效替代旧决定 | 更新当前值，只留仍必要的历史理由 |
| 只完成实施，验证未结束 | 更新进度，保留未完成验证 |
| 完整结果和关联仍在 K | 可以暂不复制；仅名称出现不算完整 |
| 已有确认可用的恢复产物 | 可收缩细节，保留必要条件和恢复入口 |
| 事项结束、取消或被替代，且没有其他继续用途 | 可以退役，包括其内部互相引用的整组内容 |
| 结束组中仍有结果被其他有效工作需要 | 保留所需的最小自包含结果，无需保留整个旧组 |
| 没有边、长期未访问、低度数或无法从当前子任务到达 | 不足以单独决定删除 |
| 重要信息是否失效仍不明 | 保留简洁结果与具体不确定性，不凭空宣告结束 |

不等待引用清零，不用循环关系让旧事项永久存活，也不实施引用计数、TTL、访问衰减或图遍历算法。图可能漏边，因此可达性与不可达性都不能替代来源和工作状态判断。

## 4. 实现边界与接口

### 4.1 复用现有所有权

继续使用 `src/engine/types.ts` 的 `Slot = { id: string; text: string }` 和现有 `Memory`。普通文本与关系表达都直接存在 `slot.text`，只有一份状态。

维护模型消费冻结 F/M/B/K，提出既有 `add/remove/priority/required` 及可选 `toolResultEdits`。`parsePatch()`、`applyPatch()`、`renderMemory()` 继续负责现有结构、整条选择及呈现；Pi 负责原有提交和持久化。没有正文与图双写，也没有新增节点表、索引或中间文件。

来源权限、完整提取输入、有效 K 修订、合法连续后缀、工具关联、冻结切点/no-recut、真实请求容量、取消、版本冲突、未确认保存和恢复行为均不变。维护仍按既有生命周期进行，不新增每 N 轮调用或后台审查；正常主动工具也不因此变成每轮必用。

### 4.2 slots 与必要项

必要结果及理解它所需的限定共同保留。允许适度重复对象名称和短条件，避免关键关系依赖可选条目。存储 ID 不作为稳定业务实体 ID；不增加跨 slot 引用协议。

`required` 每次重新判断，保护本次模型声明的必要集合；代码不能证明候选语义完整。图式内容没有永久保留资格，项目成员关系也不能自动使所有条目 required。

必要项超过软目标时保持既有弹性行为；显式硬限制及其他真实容量限制仍生效。主动 `nunc_memory_patch` 保持原增长限制和 revision 规则，不获得维护响应中的 required 参数或额外增长权限。

## 5. 增长控制和逃生方式

### 5.1 在原有维护内收缩

观察到重复元信息、旧版本持续累加、已结束组仍保留过程，或 M 增长挤压有效原文时，检查受影响的内容是否能降低粒度。使用已有 M、target、K 和容量观察即可，不加节点统计、增长评分或新警报服务。

对仍有用途的事项，保留最小可用状态，删除不再服务该用途的过程、重复和关系细节。对已经无继续用途的事项整组退役。无必要时不改未变条目，不为格式统一重写全部 M。

图式表达过于昂贵或难维护时，可在同次更新中退回普通文本。回退保持必要语义，不借简化之名删除数量、否定或未完成义务。不新增 graph mode、开关或独立收缩调用。

### 5.2 人工恢复与显式硬限制

保留并说明已有 Slots 编辑器和 memory patch 的恢复路径。模型未能可靠收缩时，通过删除、缩短、合并等不增长操作处理超目标状态，保留其他工作的必要部分。不新增自动清空或自动取消义务的操作。

保留当前默认弹性，不新增自动硬帽。显式配置的 `memory.hardMaxTokens` 继续约束维护候选，必要集合放不下时沿用 `CAPACITY` 失败。它不提供正确遗忘能力，不自动截断旧 M，也不保证已保存 M 立即缩小。

当前代码 `src/engine/accounting.ts` 的 `memoryTarget()` 默认8192，`hardMemoryLimit()` 未配置时返回 null；`src/pi/config.ts` 只传入显式硬限制。实施时纠正 `docs/CAPACITY.md` 中默认硬限制8192的错误说明，不修改代码默认值。

### 5.3 无法兼得的边界

真正必要的信息持续增加时，固定有限容量、没有可用外部恢复来源、全部细节无损保留无法同时保证。应明确报告容量与内容冲突，决定是否增加容量、收窄同时维持的工作范围或接受具体细节损失；不静默去掉必要条件来通过预算。

本方案不把退休原文额外写进归档文件补偿记忆，也不假设主 agent 可以读取任意原生 session 历史。既有项目产物只有在位置、用途和读取方式已确认时才算恢复入口。必要的用户决策仅针对真实含义或容量取舍，不为每次正常退役增加审批。

## 7. 成本相称的验证与采用

### 7.1 一个改动，一份完整交付

由同一实现 owner 完成提示、工具说明、文档和必要检查，交付一个可回退的变更。直接实现本轮确定的内容，不先做抽象框架、功能开关或并行产品变体。

生产文案保留有实际内容判断作用的规则，合并重复要求；不搬入整份设计、研究综述或测试情节，不要求模型输出逐边理由和内部检查过程。源码与文档交付完成后，真实模型验证由后续独立 live 观察执行。

### 7.2 复用机械证据

运行实际受影响的构建、policy 加载和请求构造检查；复用仍适用的 slot 更新、必要集合、显式硬限制与提交测试。不为未改代码重跑全部库存，不添加提示关键词、图格式或自报 PASS 断言。

### 7.3 三组旧版／新版行为验证

做三组独立于 MemoryArena 的多阶段情节。使用同一个模型设置，旧版与新版各运行每组一次，共六条运行分支。两版使用相同起始来源、旧 M、后续交付、切点规则和预算；第一轮维护后分别使用本分支实际生成的 M，不伪造或替换为预期记忆。

| 情节 | 检查内容 |
|---|---|
| 多对象续做 | A 已交付结果，当前处理 B；维护后再引用 A。核对主体、值、范围和否定条件，同名不同对象不混淆 |
| 连续修订 | 先形成非空 M，再局部修改同一决定并继续维护；旧值退出，未改条件和未完成验证保留，不能持续追加全部旧版本 |
| 结束、互引与收缩 | 一组事项结束且内部仍互相引用，另有外部有效工作只需要其中一个结果；退役无用细节，保住外部需要，收缩为普通文本后仍能正确续做 |

每组覆盖不止一次维护。后续问题及预期答案不提前给提取模型。复用现有调用、会话记录和人工核对能力，不建立新的评估框架、模型裁判或 graph/plain 开关。

记录实际提取候选、保存结果、后续回答、M/K 估算、调用次数、耗时和用量。分别判断提取、保存和使用错误，不能只看汇总分数；有依赖关系的错误不算独立样本。执行前固定情节与有限时间/用量上限。

不跑多模型、多参数矩阵，不追加独立图式／纯文本实验。在三组多维护情节之后，对冻结实现执行且仅执行一次用户明确授权的 fresh isolated MemoryArena native/Nunc 对照，保持 3 组共 23 travelers/arm、6 真实持久会话、46 deliveries 既有协议，不为预设分数重跑，不 benchmark 后调参。本交付不包含未授权的模型调用，真实模型观察由后续独立观察执行。遇到具体失败先诊断并修正；只有实际修改或未解决问题需要新证据时才重测。

### 7.4 完成标准

机械合同保持通过；三组行为观察分别检查关联保留、连续修订和结束事项退役。必要条件不能因收缩丢失，旧状态不能持续堆积。报告同时给出成本与失败，不用格式、节点数量、维护前 PS 或自报 PASS 代替效果证据。

实现出现缺陷，由同一 owner 修正并完成相关验证，不通过增加图服务、额外维护调用或新框架绕开问题。若观察仍不足以支持质量改善，应明确报告已实现内容和未解决的行为缺口，不能宣称改善已经证明。

六条分支只能提供所覆盖范围的证据，不承诺所有未来任务的收益或无损记忆。不做的机制不会因为一次失败自动进入实施范围。

## 8. 相关方法的有限借鉴

[AriGraph](https://arxiv.org/abs/2407.04363) 的关系与情节记忆、[A-MEM](https://arxiv.org/abs/2502.12110) 的笔记链接、[Zep/Graphiti](https://arxiv.org/abs/2501.13956) 的时效关系，提供了表达与更新思路。[Mem0/Mem0ᵍ](https://arxiv.org/abs/2504.19413) 也显示图的收益随任务类型变化，并带来额外成本。

本方案仅借鉴有当前消费者的内容组织思路。外部存储和按需检索系统的结果，不能直接证明把图放进每次全量注入的 M 更有效；研究名称不构成引入相应架构的理由。
